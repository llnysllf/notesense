# ADR 0026: Add Lockfile Supply-Chain Policy

## Status

Accepted

## Context

NoteSense already runs npm audit, dependency license checks, Dependency Review, pinned workflow-action checks, workflow token-permission checks, and repository governance checks. Those controls catch vulnerable packages, invalid licenses, and unsafe workflow drift, but the committed npm lockfile is also part of the trusted supply-chain boundary.

The lockfile should remain deterministic, generated by the pinned npm runtime, and limited to registry-hosted package tarballs with Subresource Integrity metadata. A local check gives reviewers immediate feedback before a dependency or runtime change reaches GitHub Actions.

## Decision

Add `npm run security:lockfile`, backed by `scripts/check-lockfile-supply-chain.mjs`.

The policy verifies:

- `package-lock.json` uses lockfile version 3 with `requires: true`
- the root lockfile metadata matches `package.json`
- `packageManager` remains on npm 10.x for the current lockfile contract
- package entries stay under `node_modules`
- link dependencies are not committed
- every package resolves from an `https://registry.npmjs.org/` tarball
- every package has `sha512` integrity metadata

Add `npm run security:supply-chain` to combine audit, lockfile, license, and workflow policy checks, and make `npm run verify` call that combined gate. ADR 0054 later adds SBOM generation to the same supply-chain gate.

## Consequences

- Dependency, lockfile, Node, and npm runtime changes now have a deterministic local supply-chain gate.
- Non-registry package sources require an intentional policy change before they can be committed.
- Future package-manager upgrades must update this policy, `.nvmrc`, package engines, workflows, and release documentation together.
