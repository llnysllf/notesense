# Internationalization And Localization Contract

NoteSense is English-only today. This contract keeps that boundary explicit while making future localization work deliberate, testable, and accessible instead of retrofitted under pressure.

Product-scope expectations live in [PRODUCT_SCOPE.md](PRODUCT_SCOPE.md).

## Current Language Boundary

- The current supported interface language is English.
- The root HTML document declares `lang="en"`.
- Product copy, metadata, screenshots, issue templates, and docs are maintained in English.
- No translated UI, locale selector, remote translation service, or runtime locale negotiation is part of the current product scope.
- Western note names (`A` through `G`) and octave labels (`C4` through `B4`) are the current music-learning notation contract.

## Locale Readiness Rules

- Do not add a second language by scattering translated strings through components.
- A second supported interface language requires a typed message catalog or equivalent central message layer before UI copy is translated.
- Locale selection must have a product reason, persistence plan, accessibility review, fallback behavior, and release evidence before implementation.
- Translatable messages should avoid concatenating sentence fragments at render time.
- User-visible dates, numbers, percentages, durations, and list formatting should use reviewed `Intl.*` formatting when localization begins.
- Localized copy must preserve the existing local-first privacy boundary and must not introduce analytics, network translation calls, cookies, or third-party scripts.

## Music-Learning Localization

- Note names, octave labels, clef names, and practice instructions are learning content, not just UI labels.
- Any future solfege, fixed-do, movable-do, alternate notation, or translated music vocabulary work must update product scope, accessibility, testing, release, and data-contract guidance together.
- Future localization must not silently reinterpret stored progress, exported JSON, note IDs, pitch IDs, or mastery keys.
- Data identifiers should remain stable internal IDs; translated labels should be presentation-only.

## Accessibility And Layout

- Localized copy must preserve accessible names, headings, live-region meaning, focus order, and keyboard workflows.
- Longer translated labels must fit mobile widths without horizontal overflow.
- Right-to-left language support is not currently supported; adding it requires explicit layout, visual-regression, browser-support, and accessibility evidence.
- Future translation work must include screen-reader review for changed accessible names and pronunciation-sensitive learning content.

## Change Rules

- Run `npm run i18n:check` after language, locale, copy extraction, metadata-language, translation, notation-label, text-formatting, or locale-formatting changes.
- Run `npm run accessibility:check` after localized copy changes that affect labels, headings, live regions, focus order, or screen-reader meaning.
- Run `npm run browsers:check` and `npm run test:e2e` when locale behavior affects browser workflows, responsive layout, or supported browser assumptions.
- Update this contract, product scope, quality, release, architecture, testing, accessibility, data-contract, privacy, ADR, changelog, and PR review guidance together when localization expectations change.

## Verification

`npm run i18n:check` verifies that:

- the current English-only language boundary stays explicit
- `index.html` keeps `lang="en"` until a reviewed locale strategy replaces it
- future localization rules cover message ownership, `Intl.*` formatting, accessibility, layout, data stability, privacy, release evidence, and review guidance
- README, contributing, product-scope, quality, release, architecture, testing, accessibility, browser-support, data, privacy, ADR, changelog, and PR review guidance stay connected to i18n and l10n expectations
